# v0.9.4 CSS 架构收敛计划

## 目标与用户场景

高三学生和家长会在手机、Windows 浏览器和窄屏设备上查看成绩、整理考试并生成分享页。当前首页同时加载 8 个历史 CSS 文件，用户看不到这些请求，却承受了请求数、覆盖顺序和缓存失配带来的风险：同一个按钮可能由多个版本规则共同决定，出现问题时也难以判断是哪一层造成的。

本版本的目标不是再做一套视觉，而是让现有 UI 有一个清楚、可维护、可回滚的运行时入口：信息层级、分享页钢笔风格、Logo B、移动端触控和无障碍行为保持不变；产品团队可以在一个入口中定位基础、组件和页面规则。

## 人本目标

- 学生和家长不应因 CSS 重复覆盖看到闪烁、错位或不同终端表现不一致。
- 维护者能快速找到规则来源，减少“改一处、坏另一处”的回归成本。
- 任何样式收敛都必须可撤销；历史源文件保留，用户数据、分享白名单和权限边界不受影响。
- 继续遵守触控目标至少 44px、键盘焦点、减少动效/透明度、高对比度偏好。

## 架构决策与影响

### 数据/API

无 KV、认证、Schema、比较算法或 API 变化。仅更新前端资源版本和健康检查中的 `APP_VERSION`。

### 运行时资源

将当前 `index.html` 中按既有顺序加载的 8 个 CSS 源文件编译为 `/css/app-v094.css`，入口只保留一个 stylesheet 请求。合并顺序严格保持现状，以避免级联优先级变化；旧文件继续留在仓库，作为审计和回滚源，但不再由入口加载。

### 设计令牌

在 bundle 顶部增加一组不改变现有外观的共享 CSS 变量（墨色、弱化文字、强调色、表面、边界、间距、触控尺寸）。本版本只建立稳定命名和审计入口，不进行大规模值替换；后续迁移可以逐组件完成。

## 分阶段任务与验收标准

### S0 — 实时基线与分支

- 从最新 `main` SHA 创建 `feat/css-architecture-v094`。
- 读取最新 checkpoint、开放 PR、Actions 和生产健康状态。

验收：分支父提交等于实时 `main`；工作区无用户未提交修改；基线事实记录在 checkpoint。

### S1 — 计划与版本契约

- 写入本计划和 `.codex/progress/css-architecture-v094.json`。
- 版本统一升级到 `0.9.4`：`package.json`、lockfile、`wrangler.toml`、CHANGELOG。

验收：版本契约测试只接受 `0.9.4`；健康检查继续声明 Schema 1 和 Workers KV。

### S2 — 单一运行时 CSS 入口

- 新建 `public/css/app-v094.css`，按 `styles → onboarding-v050 → ui-v050 → ui-v070 → ui-v080 → ui-v081-share-ink → brand-logo-b → ui-v092-share-delivery` 原顺序拼接。
- 入口只引用 `/css/app-v094.css`，移除 8 个历史 stylesheet 引用。
- 保留历史 CSS 文件，不删除、不覆盖；禁止 bundle 内 `@import` 和外部资源依赖。

验收：首页只有一个 CSS 请求；bundle 包含现有关键选择器、分享钢笔风格、Logo B、动效/透明度/对比度和移动端触控规则；旧源文件仍可读。

### S3 — 回归契约与浏览器覆盖

- 新增 CSS 架构测试，验证入口、bundle、令牌、无 `@import`、旧源保留。
- 更新历史版本测试中的入口和版本断言，使其检查新 bundle，而不是要求旧文件继续被加载。
- 运行单元/API/Schema/KV/分享白名单/草稿恢复/删除撤销/比较口径测试，并执行 Chromium/WebKit 多宽度浏览器回归。

验收：`npm ci` 和 `npm run verify` 全绿；360、390、430、768、1024、1280、1440 宽度下首页与分享页无横向溢出，键盘焦点可见，触控目标不小于 44px。

### S4 — PR、审查与合并

- 提交可追踪 commit，PR 描述完整复制本计划、影响边界、测试和回滚方法。
- 仅在 PR 专属 CI 通过后，根据 GitHub 实际 `expected_head` 合并。

验收：PR 分支 head 与待合并 commit SHA 完全一致；不使用强制 push 或猜测状态。

### S5 — main、部署与生产证明

- 合并后重新读取 `main` SHA，等待 main CI 和部署成功。
- 验证 `/api/health` 的 `appVersion=0.9.4`、`buildSha` 等于合并后的 main SHA、`schemaVersion=1`、`storage=workers-kv`。
- 检查生产首页只引用 `/css/app-v094.css`，并对入口和递归模块资源做逐字节验证。
- 最后更新 checkpoint，记录合并、CI、部署和生产证据。

## 风险、回滚与停止条件

- **级联顺序风险**：bundle 严格复现现有顺序；若视觉回归，恢复入口到旧 8 文件即可，旧源文件一直保留。
- **缓存风险**：使用带版本号的 `/css/app-v094.css`；若生产仍返回旧资源，停止合并后的“完成”结论并重新核验部署。
- **测试过时风险**：只调整测试的资源入口断言，不改变业务断言；任何 API/KV/分享白名单失败都停止并回退。
- **网络/权限风险**：GitHub、CI 或生产返回未知时记录命令和 SHA，不将未知视为成功，等待网络恢复或请求权限。

## 测试方案

1. 静态契约：入口 stylesheet 数量、bundle 内容、版本、无障碍偏好、旧源可回滚。
2. `npm ci`、`npm run verify`（语法检查 + 全量 Node 测试）。
3. 生产资源递归校验：入口、动态 import、CSS bundle 逐字节与本地构建一致。
4. 浏览器回归：Chromium/WebKit；360/390/430/768/1024/1280/1440；分享总成绩、单科、时间轴、键盘、触控与减少动效偏好。
5. 部署后健康检查和首页资源检查，证据写回 checkpoint。
