# v0.12.29 Record-first / change-visible product revision

## Context

Recent review of current score-record products (including long-term exam logs, comparison-oriented recorders and lightweight grade trackers) points to a common product pattern:

- The stored unit is an **exam event**, not an isolated score.
- The first useful reading is **this result + change from the previous comparable result**.
- A long-term record is most useful when the timeline remains easy to scan.
- Detail and sharing should reuse the same facts instead of creating a second interpretation layer.
- UI should favor readable rows, deltas and chronology over dashboard density.

This patch adapts those ideas to the existing 高三坐标 architecture without changing Score data Schema 1, storage, authentication, sharing permissions, or comparison eligibility rules.

## Scope

### P0 — Make change visible beside the recorded fact

1. Centralize compact human-readable metric deltas in `public/record-reading-v130.js`.
2. On the private overview, keep the current exam as the visual anchor and show a direct score delta when the previous comparable exam has both scores.
3. On six-subject rows, show a subject score delta only when both exams contain comparable subject scores. Do not place a ranking delta beside a score.
4. On the private timeline and exam detail, show per-exam / per-subject score changes only where the source data supports them.

### P0 — Keep the same reading model on shared pages

5. Public/shared total and timeline views expose the same compact score-change fact only when the shared whitelist contains the required score fields.
6. Never infer a change from hidden fields; white-list projection remains the boundary.
7. Preserve current baseline / no-comparison wording when there is not enough data.

### P1 — Product-language and UI consistency

8. Use one vocabulary for change chips: current fact first, then `比上一场 +N 分` / `比上一场低 N 分` / `和上一场接近`.
9. Keep ranking and score semantics separate. A ranking movement must not be rendered as a score delta.
10. Keep the existing restrained layout; no new chart-heavy dashboard, no color-as-data semantics, and no schema migration.

### P1 — Regression coverage

11. Add pure-function tests for score/rank/percentile delta presentation and no-data behavior.
12. Add private/public source contracts verifying the delta is only emitted from visible data and the latest-comparable selection is reused.
13. Extend browser share regression to cover the new compact delta reading and mobile layout.
14. Run `npm verify` and the full Chromium 360/390/768/1280 + WebKit 390 browser suite.

## Explicit non-goals

- No Score Schema 2 migration.
- No change to comparison eligibility or ranking algorithms.
- No introduction of an AI analysis layer.
- No forced charts or large visual redesign.
- No change to authentication, KV, Durable Object, Secret Share or deployment semantics.
